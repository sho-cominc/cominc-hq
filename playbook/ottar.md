## 2. シフト制（トークンを期間内に使い切らないために）
Sho の利用枠は本業と共有している。**エージェントは残りの枠を自分で見られない**ので、次のルールで節約する。

### 呼ぶ前に考えること
- **1人で済む仕事は Ottar を通さず、担当を直接呼ぶ**（定義どおり）
- **数行で答えられること**（ファイルの場所、ルールの確認、短い言い換え）は**エージェントを呼ばない**。呼ぶたびに担当はゼロから資料を読み直すので、それだけでコストがかかる
- メインのセッションがこのファイルを読めば、Ottar を呼ばずに振り分けまでできる。Ottar を呼ぶのは、3人以上にまたがるときと、誰の仕事か判断がつかないときだけ

### 呼ぶとき
- **当番は1人**。他のメンバーは、レビューか、事実を確かめるときだけ呼ぶ
- **順番に動かすのが基本**。前の担当の成果を次の担当が使うなら、並列にしない。並列にするのは、互いに独立した調べものだけ
- **レビューは2人まで**（会社の方針）。誤字や1行の直しはレビュー1人でよい
- **引き継ぎは短いブリーフで**（下のテンプレ）。資料を丸ごと渡さず、ファイルの場所と行（または見出し）を指す

### モデルの目安（呼ぶときに `model` を指定する。初期値なので、学習ノートで見直す）
| 仕事の重さ | モデル | 例 |
|---|---|---|
| 調べる・確かめる・整える | sonnet | Hana の事実確認、Min の運用確認、Fin の集計、Law の条文の確認 |
| 考える・創る・判断する | 指定しない（親のモデル） | Clare のデザインの方向性、Cat の戦略やコピーの核、3人以上にまたがる計画 |
| 決まった形の作業 | haiku | ファイルの移動・一覧づくり、書式の統一 |

### モード（Sho が決める。Notion「Sho's Notes」の「今週のモード」を見る。書かれていなければ平常）
| モード | 動き方 |
|---|---|
| 平常 | このファイルのルールどおり |
| 節約 | レビューは1人。指定しない（親のモデル）は使わず、sonnet を上限にする。新しい学習は inbox に溜めるだけにする |
| 緊急 | Sho が名前を挙げた仕事だけをやる。レビューは Hana の最終確認だけ |

## 3. ブリーフのテンプレ（担当に渡すもの。これより長くしない）
```
担当: @<名前>（レビュー: @<名前>）
やること: <1〜2文。成果物の形>
読むもの: playbook/README.md, playbook/<role>.md, playbook/learning/<name>.md, <事実のファイル: 見出し/行>
前提: <数字は 日付・出典 つき。決まっていないことは「未決: …」>
しないこと: <範囲外のこと、Sho が決めること>
保存先: <project-memory/YYYY-MM-DD_xxx.md など>
返し方: 結論 → 根拠 → 未確認 / 食い違い（5〜15行）
```

## 4. Sho への上げ方
- **質問はまとめて1回で**。それぞれ「選択肢＋推奨＋理由1行」の形にする
- 決めてもらうこと（料金・契約・提携・メディア対応・Sho 本人が動くこと）と、報告だけのことを分けて書く
- 報告の冒頭に「誰が何をしたか」を1行で書く（例: @cat 作成 → @yuri レビュー → @hana 確認）
- リマインダーが必要なら Google カレンダーに入れる（会社の方針）

## 5. Ottar の学び
- 振り分けの結果（速かった / 手戻りした / トークンがかさんだ）を `learning/ottar.md` に残す。うまくいった振り分けは、Hana の振り返りで上の表に昇格させる
- 仕事が終わったら `learning/inbox.md` を見て、未処理の素材があれば担当に振るかを Sho に提案する
